GEOVANI — TECHNICAL PRODUCT REQUIREMENTS DOCUMENT
Production-oriented technical blueprint for the GEOVANI demo and future deployable system
1. Technical Objective
Define the technical architecture and implementation contract for GEOVANI: an evidence-first mining intelligence platform that ingests heterogeneous mining records and structured mine data, performs document intelligence and domain enrichment, creates multimodal retrieval representations, retrieves and verifies evidence, and exposes three outputs: AI Query & Evidence, Automated Report Generation, and Document/Topic Intelligence. The frontend demo may use mock services, while the architecture must remain compatible with a future production backend.
2. System Architecture
Logical flow: Users → API Gateway/Application Backend → Ingestion & Processing → Object Storage + PostgreSQL/pgvector → Hybrid Retrieval → Reranking → Retrieval Verification → Private LLM/vLLM → Query/Report/Intelligence modules → Evidence-linked outputs.
Original files: object storage.
Structured metadata, document records, extracted entities, chunks and application data: PostgreSQL.
Vector representations: pgvector inside PostgreSQL or an equivalent vector store.
Search: combine metadata filtering, keyword/full-text retrieval and vector similarity.
LLM inference: private/on-prem vLLM for sensitive production deployment; demo can use mock generation.
Human approval should be available for important operational/management reports.
3. Data Sources
PDF and scanned PDF reports.
DOC/DOCX notes and reports.
XLSX/CSV structured data.
Images and geological maps.
Historical archives.
Parliamentary/management query documents.
SAP or equivalent structured mine/enterprise data.
Future connectors should support scheduled and incremental ingestion.
4. Ingestion Pipeline
Receive file or structured data event.
Validate extension, MIME type, size and checksum.
Store original object before transformation.
Detect document type and processing route.
Run OCR for scanned/image-based pages.
Run layout analysis to identify headings, paragraphs, tables, figures and page regions.
Extract tables into structured records.
Detect/classify figures and maps; retain page and bounding-box references.
Normalize text and preserve page/section coordinates.
Run domain entity extraction and metadata enrichment.
Create semantic chunks for text/table/figure/map content.
Generate embeddings for searchable content.
Persist chunks, metadata, embeddings and provenance.
Mark document Indexed only after all required stages succeed.
5. Document Intelligence Technical Requirements
Page-level provenance is mandatory.
Each extracted item must retain document_id, page_number, section, source type and optional bounding box.
Support OCR confidence/error flags at page or block level.
Tables should retain headers, rows and source page.
Figures/maps should retain image reference, caption, page and extracted tags.
Entity enrichment should support mine, subsidiary, location, year, production, equipment, seam, geological entity, topic and keywords.
Processing errors must be retryable without duplicating the document.
6. Chunking Strategy
Prefer semantic/section-aware chunking instead of blind fixed-size splitting.
Do not mix unrelated sections, tables or figures into one chunk.
Chunk metadata must include document_id, page, section, year, mine, subsidiary, source type and entity tags.
Tables can be represented as structured chunks plus a textual summary for retrieval.
Figures/maps should have caption/description chunks linked to the original visual.
Every chunk receives a stable chunk_id and provenance pointer.
7. Embedding & Indexing
Use a domain-capable multilingual embedding model suitable for English/Hindi/Marathi if multilingual queries are required.
Store embedding vector, model/version identifier and chunk metadata.
Create database indexes for metadata filtering and full-text search.
Maintain embedding version so re-indexing can occur after model changes.
Do not silently mix embeddings generated by incompatible models.
8. Retrieval Architecture
Use hybrid retrieval rather than relying on a single vector similarity lookup.
Step 1: Query normalization and intent/topic extraction.
Step 2: Apply metadata filters such as mine, subsidiary, year and document type when supplied.
Step 3: Run vector similarity retrieval.
Step 4: Run keyword/full-text retrieval.
Step 5: Merge candidates.
Step 6: Rerank candidates using a cross-encoder or equivalent relevance model.
Step 7: Send top candidates to Retrieval Verification.
Step 8: Only verified evidence is eligible for final generation.
9. Retrieval Verification Layer
Purpose: detect cases where retrieved chunks are semantically or contextually wrong.
Check query/chunk relevance.
Check metadata compatibility: mine, year, subsidiary, report type and other explicit constraints.
Check source provenance and page availability.
Check duplicate/conflicting evidence where applicable.
Assign candidate state: Verified, Rejected, Needs Review.
Keep rejected candidates in an audit trace for debugging.
If insufficient verified evidence remains, return an evidence-insufficient response instead of inventing an answer.
10. AI Answer Generation
Prompt contains the user query, verified evidence, provenance metadata and response constraints.
Generation must be grounded in supplied evidence.
Answer should include concise conclusion, key findings and source references.
Every material factual statement should be traceable to one or more evidence items.
Unsupported claims should be omitted or explicitly marked as unavailable.
Store query, retrieved candidate IDs, verification results and answer metadata for auditability.
11. Multimodal RAG
Text retrieval for narrative content.
Table retrieval for structured numeric information.
Figure/map retrieval using captions, tags and visual representations.
Cross-modal linking through document_id/page/entity metadata.
Production architecture should allow a multimodal model to reason over selected visual evidence when required.
Demo can represent multimodal retrieval using predefined local metadata and previews.
12. Three Application Modules
12.1 AI Query & Evidence
Question → intent → hybrid retrieval → reranking → verification → grounded answer.
Evidence drawer must open original document/page context.
Query history and saved questions can be stored.
12.2 Automated Report Generation
Report request → source selection → retrieval → verification → analysis → chart/table generation → document composition.
Reports must carry source references and report ID.
Important reports should support human approval before finalization.
12.3 Document & Topic Intelligence
Aggregate indexed metadata, entities and topics.
Generate keyword/topic distributions, year trends, mine/subsidiary breakdowns and related-document views.
All displayed insights should link back to source documents.

15. Backend API Contract
POST /api/documents/upload — create upload job and return document_id.
GET /api/documents — list/search documents.
GET /api/documents/:id — document metadata and processing status.
GET /api/documents/:id/intelligence — OCR, entities, tables, figures and topics.
POST /api/query — execute retrieval + verification + grounded answer.
GET /api/query/:id — retrieve query trace and evidence.
GET /api/evidence/:id — source/page evidence details.
POST /api/reports — create report job.
GET /api/reports/:id — report status and metadata.
GET /api/reports/:id/preview — report preview.
GET /api/intelligence/topics — topic/trend data.
GET /api/health — service health.
16. Async Processing & Jobs
Use a queue for OCR, parsing, embedding, indexing and report-generation jobs.
Recommended logical states: QUEUED → PROCESSING → COMPLETED / FAILED.
Jobs must be idempotent.
Retry transient failures with bounded retry count.
Expose job progress to frontend through polling, Server-Sent Events or WebSocket.
Keep long-running report generation outside synchronous HTTP request timeouts.
17. Security & Confidentiality
Production deployment should keep sensitive mining data inside the organization-controlled network wherever policy requires.
Use private/on-prem inference for sensitive LLM processing.
Encrypt data in transit and at rest.
Use role-based access control and least privilege.
Separate document access permissions from application permissions.
Log access to sensitive documents and generated reports.
Use secrets management; never hard-code credentials.
Apply network segmentation between ingestion, storage and inference services.
Security must be validated through organizational controls; do not claim absolute 'zero leakage'.
18. SAP / Structured Data Integration
Use a controlled connector/service account with least-privilege access.
Normalize SAP records into an internal canonical schema.
Keep source-system IDs and timestamps for provenance.
Support incremental sync based on changed records/timestamps.
Do not copy unnecessary sensitive fields into the AI index.
Structured values can be queried directly with SQL and combined with document evidence.
19. Observability & Audit
Log ingestion stages, processing failures, retrieval candidates, verification decisions and report jobs.
Metrics: ingestion success rate, processing latency, retrieval latency, verification rejection rate, report generation time and error rate.
Trace each answer to query_id → retrieval_run → chunk_ids → document/page.
Monitor model/version changes and embedding versions.
20. Production Deployment Blueprint
Frontend: React/Vite served through a hardened web server/reverse proxy.
Backend API: containerized service.
Worker services: OCR/parser, enrichment, embedding and report workers.
Queue/cache: Redis-compatible service.
Database: PostgreSQL + pgvector.
Object storage: S3-compatible private object store or approved enterprise storage.
LLM inference: private vLLM cluster/GPU server.
Reverse proxy/API gateway: TLS termination, rate limits and routing.
Deployment can be on-prem/private cloud depending on organizational requirements.
21. Frontend ↔ Backend Demo Boundary
Demo frontend should expose service interfaces identical to future production APIs.
During demo, services can be replaced by mock adapters.
mockRagService returns candidates and verification results.
mockProcessingService simulates document stages.
mockReportService generates report preview metadata.
Keep mock and production service interfaces compatible so the UI does not need to be rewritten.
22. Performance Targets for Future Production
Define targets after real dataset profiling; do not present these as achieved GEOVANI benchmarks.
Track p50/p95 API latency, retrieval latency, document-processing throughput and report-generation time.
Set separate SLOs for interactive queries versus long-running ingestion/report jobs.
Load-test retrieval and document processing using representative enterprise documents.
23. Failure Handling
OCR failure → flag page and allow retry/manual review.
Parsing failure → retain original file and mark document partially processed.
Embedding failure → retry job without duplicating chunks.
Retrieval has insufficient evidence → return evidence-insufficient response.
Verification rejects all candidates → do not generate an unsupported answer.
LLM failure → preserve retrieval/evidence results and allow retry.
Report generation failure → keep source selection and allow regeneration.
24. Technical Definition of Done
All ingestion stages have defined inputs, outputs and failure states.
Every chunk and answer has provenance.
Hybrid retrieval and reranking are separated from verification.
Verification can reject an incorrect candidate.
Grounded answers cannot be generated from zero verified evidence.
Report artifacts preserve source references.
All services are versioned and observable.
Production architecture supports private deployment for sensitive data.
Frontend demo can use mock adapters without changing page/component contracts.
25. Reference Architecture Summary
Users → Frontend → API Gateway → Query/Report Service → Hybrid Retrieval → Reranker → Retrieval Verification → Private LLM → Evidence-linked Output. In parallel, uploaded files and structured enterprise data enter the ingestion pipeline → OCR/Layout/Table/Figure extraction → Domain Enrichment → Semantic Chunking → Embeddings → PostgreSQL/pgvector + Object Storage. The same multimodal knowledge layer serves AI Query & Evidence, Automated Reports, and Document/Topic Intelligence.
26. Important Technical Principle
Evidence first, generation second.
GEOVANI should treat retrieval and evidence verification as first-class system components. The LLM is the reasoning/generation layer, not the source of truth. The source documents and structured enterprise data remain the authoritative evidence layer.
